# MS2 (P3 cloud side) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Finish PRD MS2 on the cloud side: SC-1 stays green, SC-2 (blocked corridor, closed gate, re-assign the last leg under a new lease version, possibly to the other cluster) and SC-3 ("Ward 2C is now isolation…") run end to end through the HTTP API, with a better agent loop behind them.

**Architecture:** Keep the existing pipeline (LLM proposes, deterministic Rule Checker disposes, one transactional commit). Add (a) a bounded multi-turn agent loop with read-only look-up tools, used by two new steps, `statement` and `react`; (b) a leg model so a task can cross clusters; (c) persistent map closures and place inventory; (d) a stand-down lease so the cloud can stop work without changing the lease contract; (e) a notice channel for answers, warnings and operator/ward messages. The model never commits: every terminal tool call is validated by code (checker, lease-zone test, schema) and has a rules-only fallback (FR-15/18).

**Tech Stack:** Python 3.11+, stdlib `http.server` (P4's `server.py`), jsonschema, boto3/moto for the AWS backend, pytest. No new dependencies.

**Spec:** `PRD.pdf` v5.0 Sec. 3 (SC-1..SC-3), Sec. 4 (FR-5, 8, 9, 11, 13, 14, 16, 17, 18, 20), Table 2 (escalations); `context/02-team-and-ownership.md`; `Team Task Distribution and Roadmap.docx` (P3 row, Phase 2).

## Decisions to confirm before coding (each changes what other people build)

| # | Decision | Why | Who must agree |
|---|---|---|---|
| D1 | **Stand-down = a higher-version lease for the same task and old cluster whose `task_sequence` is `[stop]`/park and whose `allowed_zones` is the robot's current zone.** No new field, no new message type. | The edge already honours "higher version replaces the old one" (FR-8). Keeps the 12-field contract. | P2 must confirm the supervisor parks on a `stop`-only lease. |
| D2 | **New cloud->edge topic `nimbus/{cluster}/notice`** carrying `{type: ANSWER\|WARNING\|MAP, task_id?, lease_version?, text, message_id, ts}` for CLARIFY answers, SC-2 "warn the affected cluster" and map updates. Add to `contracts/topics.md` as an optional addendum, as `renewal` and `probe` were. | PRD Table 2 lets the cloud "answer", "warn other clusters" and "update the map", but no message carries it. | P4 (contract + Terraform topic rule), P2 (consume or ignore safely). Fallback if refused: HTTP reply body of `POST /escalations` plus `GET /notifications`. |
| D3 | **A task can have legs.** Task A->B across clusters = leg 1 (cluster X, source -> hand-off zone), leg 2 (cluster Y, hand-off -> destination). Each leg is a lease version of the same task id, so versions stay monotonic. | SC-2 "re-assigns the last leg under a new lease version"; T5. | P4 sees `task["legs"]` in `GET /tasks/{id}` (additive). |
| D4 | **One message can create several tasks** (children). Parent keeps `children: [task_id]`. | Multi-item requests (FR-13) and SC-3 extraction need N tasks from one sentence. | P4: server creates child ids via `store.next_task_id`. |
| D5 | **Places hold inventory** (`fleet.json` `places`), moved on OUTPUT_READY of an extraction task. | SC-3 "get the spare pumps out of 2C" needs to know there are pumps there. | None (seed data, P3). |

If any of D1/D2 is rejected, Tasks 5 and 8 use the stated fallback; nothing else depends on it.

## Review Focus

- A gate or corridor reported closed by the edge, then a *second* request through it: must route around or hold, not lease through the closure (Task 1).
- UNEXPECTED_EVENT arriving twice, out of order, or for a stale lease version: one re-plan only, 409 for stale (Tasks 3, 4).
- Re-plan when the robot is mid-route (not at the pickup): new lease must include the robot's current zone or be refused (Task 3).
- Hand-over when the second cluster is busy, down, or out of the item: leg 2 queues, leg 1 is not abandoned (Task 4).
- Model answers a zone outside the lease, an unknown cluster, or an empty list of tasks: rejected by code, rules take over (Tasks 2, 3, 6).
- "Ward 2C is now isolation" twice, or lifted later, or naming a ward that does not exist: idempotent / asks, never half-applies (Task 6).
- A routine lease already in flight into the newly isolated ward: stood down and held, urgent untouched (Task 6).
- Cancel on a task whose lease is mid-hand-over: stand-down sent to the cluster that holds the robot (Task 5).
- Agent loop that never terminates or calls read tools forever: hard turn cap, then rules (Task 2).
